# Резервне копіювання та відновлення даних (Backup & Disaster Recovery)

**Версія документа:** 4.2.0 (Security Hardened)  
**Дата набрання чинності:** 24 жовтня 2026 року  
**Розробник комплексу:** ТОВ «МАКСІ-ЮА» (MAXI-UA LLC)  

Система **SD-GEN016** підтримує багаторівневе резервне копіювання:
1. **Вбудований веб-модуль SuperAdmin UI & REST API**: створення архівів в один клік, завантаження на ПК оператора, безпечне відновлення із завантаженого ZIP-файлу, налаштування фонового автобекапу за розкладом та автоматична ротація (видалення старих копій).
2. **Консольні CLI-скрипти**: для автоматизації на рівні хостової ОС через `cron` або CI/CD pipelines.

## 1. Вбудований бекап-центр у Веб-інтерфейсі (SuperAdmin Only)

У вкладці **«⚙️ Адміністрування»** для користувачів із роллю **Головний адміністратор (SuperAdmin)** доступний окремий блок: **«💾 Резервні копії системи (Бекапи)»**.

### 1.1. Можливості веб-інтерфейсу
- **➕ Створити бекап зараз**:
  - **Повний бекап (`full`)**: містить повний дамп усіх 20 реляційних таблиць БД у форматі JSON (`database_export.json`), фізичну базу SQLite (`service_desk.db`), папку фотографій чеків і дефектів (`uploads/`), безпечні конфігураційні файли (із маскуванням паролів), а також маніфест цілісності `manifest.json` із хеш-сумами SHA-256 та лічильниками записів.
  - **Тільки база даних (`db_only` / `partial`)**: швидкий компактний зліпок виключно реляційних даних, конфігурацій та бази даних без медіафайлів.
  - **Коментар/примітка**: можливість зафіксувати причину створення зліпка (напр. *«Перед плановим ТО генератора №1»*).
- **📥 Завантаження на робоче місце**: скачування сформованого `.zip` архіву безпосередньо через браузер із авторизацією.
- **📤 Відновлення із завантаженого архіву (Upload & Restore)**: можливість завантажити раніше збережений ZIP-архів з комп'ютера та автоматично розгорнути його на сервері.
- **🗑️ Видалення застарілих копій**: безпечне видалення з підтвердженням та захистом від Path Traversal.
- **⚙️ Розклад автобекапу**:
  - Увімкнення/вимкнення щоденного фонового демона;
  - Налаштування часу спрацьовування за часовим поясом Києва (`Europe/Kyiv`);
  - Вибір періодичності: щодня (`daily`) або щотижня (`weekly`);
  - Політика збереження (ротація): збереження N найновіших копій (за замовчуванням 7).

## 2. Безпека резервного копіювання (Security Hardening v4.2)

### 2.1. Автоматичне маскування секретів (`_copy_env_redacted`)
Під час створення повного або часткового бекапу файл оточення `.env` копіюється в архів із автоматичним приховуванням відкритих паролів. Усі рядки, що містять ключі `SECRET`, `PASSWORD`, `KEY`, `TOKEN` або `DATABASE_URL` (наприклад, `APP_SECRET_KEY`, `INITIAL_ADMIN_PASSWORD`, `POSTGRES_PASSWORD`), записуються як:
```text
APP_SECRET_KEY=***REDACTED***
INITIAL_ADMIN_PASSWORD=***REDACTED***
POSTGRES_PASSWORD=***REDACTED***
```
Це унеможливлює витік облікових даних у разі передачі чи завантаження архіву третіми особами.

### 2.2. Захист від атак на архіви (Zip Slip & Zip Bomb Defense)
Функція відновлення `_safe_extract_zip` містить обов'язкові перевірки:
1. **Zip Slip (Path Traversal)**: аналізується кожен елемент архіву (`zf.infolist()`). Назви файлів із відносними переходами `..`, абсолютними шляхами або спробами виходу за межі цільового каталогу негайно відхиляються з помилкою `ValueError`.
2. **Zip Bomb (Decompression Bomb)**:
   - Максимальна кількість файлів в архіві: **10 000**;
   - Максимальний сумарний обсяг розпакованих даних: **500 МБ**.
   Перевищення цих лімітів блокує розпакування та повертає статус помилки.

### 2.3. Контроль розміру завантаження (100 MB Limit)
Ендпоінт `POST /api/v1/backups/upload-restore` здійснює потокове зчитування файлу блоками по 64 КБ:
- Якщо розмір перевищує **100 МБ**, запис негайно переривається, тимчасовий файл видаляється, а клієнту повертається статус `413 Payload Too Large`.
- На рівні зворотного проксі Nginx директива `client_max_body_size` синхронізована на значення `100M`.

### 2.4. Автоматичний запобіжний зліпок (Pre-Restore Safety Snapshot)
Перед початком будь-якої процедури відновлення (з диска або через upload) система автоматично створює знімок стану БД (`backup_partial_..._pre_restore`). Якщо процедура відновлення з пошкодженого архіву буде перервана, адміністратор може повернутися до вихідного стану.

## 3. Специфікація REST API (/api/v1/backups)

Усі ендпоінти захищені та вимагають обов'язкової ролі **`is_superadmin = True`**:

| Метод | Ендпоінт | Опис та безпекові ліміти |
| :--- | :--- | :--- |
| `GET` | `/api/v1/backups` | Отримання списку наявних архівів, загального обсягу та SHA-256 хешів |
| `POST` | `/api/v1/backups` | Створення нового бекапу (`{"type": "full" \| "partial", "notes": "..."}`) |
| `GET` | `/api/v1/backups/{filename}/download` | Потокове безпечне завантаження ZIP-архіву |
| `GET` | `/api/v1/backups/{filename}/inspect` | Читання `manifest.json` та перевірка цілісності перед відновленням |
| `POST` | `/api/v1/backups/{filename}/restore` | Відновлення з наявного архіву на сервері (`confirmation: "ВІДНОВИТИ"`) |
| `POST` | `/api/v1/backups/upload-restore` | Завантаження ZIP з ПК та відновлення (ліміт 100 МБ, Zip Slip/Bomb захист) |
| `DELETE` | `/api/v1/backups/{filename}` | Безпечне видалення файлу бекапу з диска |
| `GET` | `/api/v1/backups/settings` | Перегляд поточних параметрів автобекапу та розкладу |
| `PUT` | `/api/v1/backups/settings` | Оновлення розкладу автобекапу (час `HH:MM`, частота, ротація) |

### Структура архіву `backup_{type}_{timestamp}.zip`:
```text
backup_full_20261024_120000.zip
├── manifest.json            # Версія, тип, автор, SHA-256 хеші, кількість рядків
├── database_export.json     # Повний дамп усіх 20 таблиць БД (JSON)
├── service_desk.db          # Фізичний файл SQLite бази даних (у режимі SQLite)
├── config/                  # Конфігурації (.env із замаскованими паролями, docker-compose)
│   ├── .env                 # APP_SECRET_KEY=***REDACTED*** тощо
│   ├── .env.example
│   ├── docker-compose.yml
│   └── nginx.conf
└── server_files/            # Вихідний код, скрипти, шаблони (у режимі full)
    └── uploads/             # Фотографії чеків, накладних та дефектів
        ├── receipts/...
        └── faults/...
```

## 4. Створення та відновлення через консоль (CLI)

### Створення резервної копії:
```bash
# Кросплатформно (Python):
python scripts/backup.py

# На Linux / VPS (Shell):
sh scripts/backup.sh
```

### Відновлення системи з резервної копії:
```bash
# Кросплатформно (Python):
python scripts/restore.py backups/backup_full_20261024_120000.zip

# На Linux / VPS (Shell):
sh scripts/restore.sh backups/backup_full_20261024_120000.zip
```

Скрипт відновлення:
1. Перевіряє цілісність та безпеку архіву (SHA-256, Zip Slip);
2. Створює запобіжний snapshot;
3. Очищує та імпортує таблиці з `database_export.json`;
4. Відновлює директорію вкладень `uploads/`;
5. Оновлює in-memory системні кеші.
