## 2. Категорії та склад даних, що обробляються Системою

Система обробляє такі групи даних:

### 2.1. Облікові та ідентифікаційні дані персоналу (Користувачі)
- **Службовий логін (Username):** унікальний буквено-цифровий ідентифікатор (3–50 символів);
- **Прізвище, ім'я та по батькові (ПІБ / Full Name):** для персоніфікації записів у журналах пусків, накладних прийому палива, актах ТО та аудиті;
- **Адреса електронної пошти (Email):** службовий контакт для сповіщень та відновлення доступу;
- **Хеш службового пароля:** зберігається виключно у вигляді незворотного криптографічного хешу за алгоритмом **bcrypt** (salt rounds = 12); відкриті паролі ніколи не фіксуються і не зберігаються;
- **Службова роль та матриця повноважень (RBAC):** перелік наданих дозволів (`superadmin`, `admin`, `operator`, `viewer`).

### 2.2. Технічні, сесійні та мережеві дані
- **Мережева адреса (IP-адреса):** фіксується при кожній авторизації, зміні пароля, операціях запуску/зупинки та коригування даних для запобігання несанкціонованому доступу;
- **Ідентифікатор браузера / пристрою (User-Agent):** використовується для розпізнавання платформи (PWA, Android, iOS Safari, Desktop) та адаптації інтерфейсу;
- **Токени автентифікації (JSON Web Tokens — JWT):** короткострокові (24 години) або довгострокові (до 60 діб при активації функції «Запам'ятати мене»);
- **Технічні файли Cookie:** системні cookie з прапорцями `HttpOnly`, `SameSite=Lax`, `Secure` (за умови HTTPS), призначені виключно для авторизації сеансу;
- **Локальний стан клієнта (Local Storage):** збереження ID останнього обраного об'єкта (`sd_last_facility_id`) та генератора (`sd_last_generator_id`), токена офлайн-доступу PWA.

### 2.3. Дані Web Push сповіщень (W3C Push API / RFC 8291, 8292)
- **Push Endpoint URI:** унікальна системна адреса доставки повідомлення, згенерована браузером пристрою (Google FCM, Mozilla Push Service, Apple Web Push);
- **Криптографічні ключі клієнта:** публічний ключ клієнта (`p256dh`) та автентифікаційний секрет (`auth`);
- **Індивідуальні налаштування категорій підписки:** перемикачі сповіщень (пуск, стоп, низький рівень пального, ТО, аварії).

### 2.4. Виробничі, технічні та локаційні дані обладнання
- **Об'єкти та локації:** назва філії/об'єкта, фізична адреса об'єкта, прив'язані склади палива та генераторні установки;
- **Параметри генератора:** марка, модель, серійний заводський номер, номінальна потужність (кВт), місткість бака (л), нормативний погодинний розхід палива (л/год), поточний статус роботи;
- **Журнал напрацювання (Мотогодини):** початкові та кінцеві покази лічильника (одометра), дата і час пуску/зупинки, точна тривалість циклу у секундах, розрахункова витрата пального;
- **Складський та фінансовий рух ПММ:** об'єм поставки (л), загальна вартість за чеком (грн), розрахункова ціна за літр (грн/л), номер ТТН / чека, ПІБ водія бензовоза, назва складу ГСМ, об'єм заправки в бак;
- **Технічне обслуговування (ТО):** вид сервісу (регламентне за мотогодинами або проміжне), дата, перелік виконаних робіт, використані запчастини/олива, вартість робіт, ПІБ виконавця;
- **Журнал аварій та дефектів:** опис несправності, рівень критичності, статус усунення, ПІБ відповідального інженера.

### 2.5. Мультимедійні вкладення (Фотофіксація)
- Фотографії фіскальних чеків, накладних, актів виконаних робіт;
- Фотографії пошкоджень, витоків палива або дефектів вузлів обладнання;
- Метадані файлів: дата завантаження, розмір, MIME-тип.

## 4. Заходи захисту інформації та технічна безпека

Розробником впроваджено комплекс організаційних та технічних заходів кіберзахисту:

4.1. **Шифрування та криптографія:**
- Усі мережеві з'єднання шифруються за протоколами **TLS 1.2 / TLS 1.3**;
- Паролі користувачів захищені алгоритмом **bcrypt** (стійким до атак за допомогою GPU);
- Токени авторизації підписуються криптографічним ключем високої ентропії (256-бітний HMAC-SHA256);
- Push-повідомлення шифруються за стандартом **ECDH на еліптичній кривій P-256**.

4.2. **Захист від мережевих та прикладних атак:**
- **Rate Limiting та Lockout:** тимчасове блокування IP-адреси та облікового запису на 300 секунд після 5 поспіль невдалих спроб входу;
- **Захист від переліку користувачів (Timing Attack Mitigation):** стабільний час серверної відповіді навіть при неіснуючому логіні;
- **Захист від SQL-ін'єкцій:** використання суворо типізованих параметризованих ORM-запитів (SQLAlchemy 2.0);
- **Захист від XSS та Formula Injection:** примусове санітизування вхідних рядків (`escapeHtml`) та очищення небезпечних префіксів формул (`=`, `+`, `-`, `@`) при експорті таблиць;
- **Політика заголовків безпеки:** використання суворих HTTP-заголовків `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`.

4.3. **Ізоляція даних та захист прав доступу (RBAC):**
- Доступ до модулів системи регулюється на рівні серверних залежностей;
- Рядові оператори позбавлені можливості редагувати або видаляти історичні записи;
- Доступ до системних коригувань залишків обмежений виключно роллю `superadmin` з обов'язковою фіксацією номера документа чи акта інвентаризації.

5.1. **Дані облікових записів:** зберігаються протягом усього строку експлуатації системи конкретним підприємством. У разі деактивації облікового запису його історичні дії в журналах зберігаються для збереження цілісності звітів.  
5.2. **Журнали пусків, паливного руху та ТО:** зберігаються не менше **3 років** (за замовчуванням — до 7 років відповідно до правил податкового та виробничого обліку України).  
5.3. **Журнали аудиту дій користувачів (Audit Logs):** зберігаються на постійній основі без можливості часткового або вибіркового редагування.  
5.4. **Web Push підписки:** автоматично деактивуються та видаляються при отриманні відповіді від push-шлюзу `410 Gone` (пристрій відписано або браузер скинув реєстрацію).  
5.5. **Резервні копії (Backups):** зберігаються у зашифрованих архівних сховищах згідно з внутрішнім регламентом резервного копіювання організації.
